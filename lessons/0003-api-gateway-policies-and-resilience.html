第三课 · API 治理

安全、流量与系统韧性

API 网关真正的价值，不是“多转发一跳”，而是把公共规则变成可执行、可观察、可回滚的策略。

约 50 分钟38 个概念6 个练习
03—A

API 路由与契约

网关首先要准确识别“这是什么调用”，才能执行正确政策。

Concept 01

API Endpoint（API 端点）

由协议、域名、路径和方法共同标识的可调用能力。

案例POST https://api.example.com/v1/orders 表示创建订单，不只是一个 URL 字符串。
Concept 02

Route Matching（路由匹配）

按 Host、路径、方法、Header 或查询参数选择规则。更具体的规则通常应优先。

案例GET /users/* 去用户服务；带 X-Canary: true 的请求去候选版本。
Concept 03

Schema Validation（结构校验）

根据 OpenAPI、JSON Schema 或 Protobuf 检查请求结构、类型和大小。

案例人数必须是整数；上传体不能超过 10 MB。网关可提前拒绝明显无效请求。
Concept 04

API Versioning（API 版本管理）

让新旧契约在迁移期并存，常用路径、Header 或媒体类型表达版本。

案例/v1/orders 保持旧字段，/v2/orders 返回新的状态模型。
Concept 05

API Inventory & Deprecation（接口清单与弃用）

知道哪些 API、版本、调用者和后端仍在使用，才能安全下线旧接口。网关日志是重要证据，但不能代替正式契约管理。

案例准备删除 v1 前，先查 30 天调用记录；发现旧版小程序仍在用，就必须继续兼容或推动升级。
03—B

身份：认证与授权绝不能混

“你是谁”和“你能做什么”是两次不同判断。

Concept 06

Authentication（认证）

验证调用者身份。结果通常是一个主体：用户、服务、设备或应用。

案例网关验证 JWT 签名、过期时间、签发者和受众，确认调用者是用户 123。
Concept 07

Authorization（授权）

身份确定后，判断主体是否允许执行某个动作或访问某个资源。

案例用户 123 可以查看自己的订单，但不能读取用户 456 的订单。
Concept 08

API Key

常用于识别调用项目、合作方或客户端应用，便于配额和计费；通常不应单独作为最终用户登录身份。

案例地图合作商 A 使用一个 API Key，平台据此计算它每月调用量。
Concept 09

Session / Cookie（会话与 Cookie）

服务端保存会话状态，客户端通过 Cookie 携带随机会话标识。网关可验证或转发，但要处理 CSRF、安全属性和注销。

案例浏览器登录后携带 HttpOnly; Secure Cookie，网关查询集中会话存储。
Concept 10

JWT（JSON Web Token）

一种可签名的 Token 格式。它不是完整认证协议；安全性取决于签名验证、密钥、有效期、受众和撤销策略。

反例只解码 JWT 内容、不验证签名，相当于相信用户自己写的身份证。
Concept 11

OAuth 2.0 与 OpenID Connect

OAuth 2.0 核心是授权委托；OpenID Connect 在其上增加身份层，用 ID Token 表达登录身份。

通俗解释OAuth 像“允许打印店读取你的云盘文件”；OIDC 像“用某身份平台登录这个网站”。
Concept 12

RBAC 与 ABAC

RBAC 按角色授权；ABAC 按用户、资源、环境等属性计算政策。

案例RBAC：“管理员可查看全部订单”；ABAC：“同一租户且订单归属本人时可查看”。
Concept 13

对象级授权

是否能访问某一个具体对象，通常需要业务数据。网关可做粗粒度检查，但业务服务必须再次校验资源归属。

职责边界网关能判断“用户角色允许访问订单 API”；订单服务判断“这张订单是否属于该用户”。
03—C

流量治理：不只是“每分钟几次”

数量、速度、并发、体积和成本是不同维度。

Concept 14

Rate Limit（速率限制）

限制单位时间内的请求速率，保护服务并建立公平性。

案例每个用户每分钟最多发送 20 条聊天消息，超出返回 429。
Concept 15

Throttle（节流）

把过快流量延迟或压低到允许速率，而不是立即全部拒绝。

通俗解释限流像门票售罄后拒绝入场；节流像地铁闸机控制放行速度。
Concept 16

Quota（配额）

较长周期内允许使用的总量，例如每天、每月的调用次数或 token。

案例免费合作方每月有 10 万次地图查询额度。
Concept 17

Concurrency Limit（并发限制）

限制同时正在执行的请求数量，对耗时任务比单纯 QPS 更有效。

案例一次模型推理要 20 秒，即使每秒只来 2 个，也可能累积 40 个并发。
Concept 18

Token Bucket / Leaky Bucket

令牌桶允许一定突发流量；漏桶更强调稳定输出速率。

案例令牌桶容量 10、每秒补 1 个：用户可以瞬间发 10 次，之后约每秒一次。
Concept 19

Resource Limit（资源限制）

限制请求体、分页大小、执行时间、文件数和解压后体积，防止资源耗尽。

案例攻击者把 page_size 从 100 改成 1,000,000，可能拖垮数据库。
Knowledge Point

限流键（Rate-limit Key）决定公平性

可以按 IP、用户、租户、API Key、路径或它们的组合限流。只按 IP 可能误伤公司共享出口；只按用户无法限制未登录攻击。

案例登录接口同时按 IP 和账号限制；普通 API 按租户加用户限制；昂贵的模型接口再加 token 成本限制。
03—D

韧性：失败时别让整个系统一起倒

分布式系统一定会失败，网关的目标是约束失败范围。

Concept 20

Timeout（超时）

等待超过预算便停止。应区分连接超时、首字节超时、请求总超时和空闲超时。

案例连接上游最多等 1 秒，整个普通 API 最多等 5 秒；流式聊天用更长的空闲超时。
Concept 21

Timeout Budget（超时预算）

整条链路的总预算要在各调用层分配，外层不应比内层更早放弃却让内层继续浪费资源。

案例客户端预算 8 秒，网关 7 秒，服务 6 秒，数据库 3 秒，并保留返回时间。
Concept 22

Retry（重试）

对暂时性失败再次尝试。只能在明确错误类型、有限次数、剩余预算充足且操作安全时使用。

反例创建订单超时后无条件重试，第一次其实已成功，最终生成两张订单。
Concept 23

Backoff & Jitter（退避与抖动）

重试间隔逐渐增大，并加入随机量，避免大量客户端同一时刻再次冲击服务。

通俗解释商店临时关门时，不要让所有顾客每秒整点同时撞门；每个人随机晚一点再来。
Concept 24

Idempotency（幂等）

相同操作执行多次，业务结果仍等价。写操作常使用幂等键和服务端结果记录实现。

案例客户端用同一 Idempotency-Key 重试支付，服务端返回第一次结果而不重复扣款。
Concept 25

Circuit Breaker（熔断器）

上游持续失败时暂时停止新调用，快速失败；一段时间后少量试探，恢复后重新放行。

通俗解释电路短路时保险丝先断开，避免整栋楼持续烧毁。
Concept 26

Bulkhead（舱壁隔离）

把连接池、线程、并发或租户容量隔开，防止一个故障域耗尽全部资源。

案例文件上传使用独立连接池，即使上传拥堵，也不占满登录 API 的全部连接。
Concept 27

Load Shedding（过载丢弃）

系统接近极限时主动拒绝低优先级工作，保住核心能力。

案例高峰期暂停推荐刷新，但继续允许支付和订单查询。
Concept 28

Fallback（降级）

主能力不可用时返回简化结果、缓存结果或切换备用服务。

案例推荐服务故障时显示热门商品，而不是让整个首页 500。
03—E

发布流量：新版本怎样安全进入生产

网关是流量开关，但发布决策必须由指标和回滚能力支撑。

Concept 29

Canary Release（金丝雀发布）

先让小比例真实流量进入新版本，根据错误率和延迟逐步扩大。

案例v2 先接 1%，稳定后依次升到 10%、50%、100%。
Concept 30

Blue-Green Deployment（蓝绿部署）

准备两套完整环境，验证新环境后一次切换入口，出现问题再切回。

案例蓝环境运行 v1，绿环境部署 v2；网关把全部流量从蓝切到绿。
Concept 31

Traffic Mirroring（流量镜像）

复制真实请求给候选系统，但候选响应不返回用户。适合验证兼容性。

注意镜像写请求可能产生副作用，必须脱敏并确保影子环境不会真的扣款或发消息。
Concept 32

Feature Flag（功能开关）

按用户、租户或比例启用功能。它可能与网关分流配合，但业务功能开关通常属于应用层。

案例网关把测试租户送到 v2；应用内开关只对该租户显示新工作流。
03—F

可观测性：从“挂了”到“哪一段为什么慢”

日志、指标和追踪不是三个同义词。

Concept 33

Access Log（访问日志）

记录一次请求发生了什么，例如时间、路径、状态码、延迟、调用者和上游。

案例查某个 Request ID，发现请求在网关排队 20 ms、上游执行 4.8 秒。
Concept 34

Metrics（指标）

对大量请求聚合统计，常关注流量、错误、延迟和饱和度。

案例过去 5 分钟 5xx 比例从 0.2% 升到 8%，P99 延迟达到 6 秒。
Concept 35

Distributed Trace（分布式追踪）

把一次请求跨网关和多个服务的各段操作组织成 Trace；每一段工作叫 Span。

案例Trace 显示总耗时 3 秒，其中订单服务 100 ms，外部地图 API 占 2.7 秒。
Concept 36

Context Propagation（上下文传播）

把 Trace ID、租户或请求上下文安全地传到后续服务，使各段记录能关联。

案例网关生成 Trace ID，FastAPI、LangGraph 和工具服务都在日志中携带它。
Concept 37

SLI / SLO

SLI 是实际指标，例如成功率；SLO 是目标，例如“每月 99.9% 请求成功”。

案例发布网关规则后，如果 5 分钟成功率低于 99.5%，自动回滚。
Concept 38

High-cardinality（高基数标签）

用户 ID、完整 URL 等取值数量巨大，不适合直接作为指标标签，否则成本和查询压力暴涨。

实践指标用规范化路由 /orders/{id}；具体订单 ID 放日志或 Trace。
03—G

控制面、数据面与策略顺序

现代网关不只是一个进程，而是一套配置和执行系统。

Architecture

Control Plane（控制面）

管理路由、证书、服务发现、插件和政策，并把配置下发到执行节点。

案例GitOps 合并一条 HTTPRoute 后，控制器生成网关配置并灰度下发。
Architecture

Data Plane（数据面）

真正处理每个连接和请求，必须低延迟、高可用，并在控制面短暂失败时继续使用最后有效配置。

案例Envoy 进程是数据面；管理它的 xDS 服务属于控制面。
Knowledge Point

策略执行顺序

典型顺序是：连接与 TLS → 请求大小 → WAF → 认证 → 授权 → 限流 → 路由 → 上游保护 → 响应政策 → 观测记录。实际产品不同，但顺序必须显式设计。

案例如果先把大型请求完整读入内存再检查大小，攻击者已经消耗资源；如果先缓存私人响应再计算用户身份，可能泄露数据。
配置作者 ──▶ 控制面 ── 配置版本 / 校验 / 下发 ──▶ 数据面 │ 客户端 ── TLS ── 认证 ── 授权 ── 限流 ── 路由 ───────┼──▶ 上游 │ Logs / Metrics / Traces
03—H

检索练习

本课信息密度最高，练习用于暴露概念混淆。

1. API Key、OAuth、OIDC 分别更接近什么用途？

API Key 常识别调用项目；OAuth 处理授权委托；OIDC 在 OAuth 2.0 上提供最终用户身份认证层。

2. 网关验证用户角色后，订单服务还需检查什么？

对象级授权，例如订单是否属于该用户或同一租户。网关不能仅凭角色替代业务数据校验。

3. Rate Limit、Quota、Concurrency Limit 的区别是什么？

分别限制单位时间速率、长周期总量和同时执行数量。

4. 为什么重试要配合退避、抖动和幂等？

退避减少持续压力，抖动避免同步重试风暴，幂等防止重复写入产生多次业务结果。

5. 熔断与限流的差别是什么？

限流控制进入系统的负载；熔断根据上游失败状态暂停调用，避免级联故障。

6. 日志、指标、追踪分别回答什么问题？

日志描述具体事件；指标展示总体趋势；追踪展示单次请求跨组件的完整路径。
