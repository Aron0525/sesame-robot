13—A

先纠正两套旧认知

先后有过不同架构，必须以当前正式代码为准。

容易混淆的说法当前项目的事实
“这是 Arduino 主工程。”不是。当前唯一正式固件是 firmware/esp32_voice_idf/，使用 ESP-IDF；firmware/arduino/ 是旧基线和动作来源。
“ASR/TTS 还是 Demo 或静音。”不是当前目标实现。Gateway 代码已包含 DashScope ASR/TTS Provider；是否真能调用取决于本机 .env 的凭据与授权。
“OpenClaw 说挥手，机器人就挥手。”当前 v1.5 网关会把 AI 输出的动作清掉；AI 只影响回复、声音风格和表情。本机控制台与 ESP32 才负责受保护的物理动作。
学习规则阅读旧课程或旧文档时，凡是与根目录 README.md、contracts/ 和当前源代码冲突的地方，都把当前代码当成事实，不把旧说明当成命令。
13—B

一次对话，实际上经过七步

这七步是之后读所有文件的坐标轴。

① 用户按 BOOT / 说唤醒词 ② ESP32：I2S 读麦克风 PCM ③ ESP32：PCM → Opus，经 WSS 发给电脑 ④ Gateway：Opus → PCM，DashScope ASR → 最终文字 ⑤ Gateway：文字 → 本机 OpenClaw → 受限 JSON 回复 ⑥ Gateway：回复文字 → DashScope TTS PCM → Opus ⑦ ESP32：播放 Opus、显示表情；必要时执行已校验的本地动作
Device

ESP32 处理实时世界

它离硬件最近，所以负责采音、播音、按键、Wi-Fi、OLED、舵机；它不需要理解“用户问了什么”。

Gateway

电脑负责编排

它是唯一同时认识设备、语音服务和 OpenClaw 的组件，因此负责验证、转换格式、调用顺序与失败处理。

OpenClaw

AI 是链路的一段，不是整个系统

它只看到 Gateway 给它的文字和允许的能力清单。它不能读取机器人录音、不能登录设备，也不能越过 Gateway 去操作硬件。

看到文件后，怎样判断它该不该改

先划清源代码、合同、配置和生成物。

类型例子通常如何对待
源代码.cpp、.h、.py实现功能；修改后需要对应测试。
构建描述CMakeLists.txt、pyproject.toml、uv.lock决定如何编译、安装和启动；不要为绕过报错随意改锁文件。

生成物/本机状态.venv、build/、managed_components/通常不手改，可从配置和工具链重新生成。
13—F

接下来的学习路线

目标不是背术语，而是每次都能沿调用链定位问题。

  1. 设备启动：从 app_main.cpp 认识对象如何被创建。
  2. FreeRTOS：任务、队列、互斥锁怎样保证实时语音不卡住。
  3. 音频：PCM、I2S、Opus、20 ms 帧为什么这样设计。
  4. 网络：Wi-Fi、mDNS、TLS、WSS、会话和重连分别解决什么问题。
  5. Gateway：FastAPI WebSocket、认证、状态与异步回合。
  6. Pipeline：ASR、OpenClaw、TTS、打断与错误如何流动。
  7. 协议与安全：JSON Schema、序号、能力白名单和三层拒绝。
  8. 动作与硬件：网页控制、舵机电源、姿态、急停与验证。
  9. 构建与部署：从新电脑到实机联调，每层如何独立验收。
  10. 测试与改动：怎样为一次小修改找到正确测试，而不被 AI 生成代码带着跑。

本课唯一要记住的话

这个项目的中心不是 OpenClaw，也不是 ESP32；中心是“受验证的语音回合”。ESP32 负责现实世界，Gateway 负责跨边界编排，OpenClaw 负责受限制的语言理解。

13—G

两分钟自测

先自己回答，再展开答案；答不上来是下一节的起点。

1. ESP32 想把录音交给 OpenClaw，能直接连接它吗？

不能。ESP32 只连接 Voice Gateway；Gateway 先完成设备鉴权、音频解码和 ASR，才把最终文本交给本机 OpenClaw。

2. contracts/ 是可启动程序吗？

不是。它是两端共同遵守的消息合同。ESP32 或 Gateway 改字段时，合同和另一端都可能需要同步。

3. 为什么 .env 不能提交到 Git？

它包含设备 token、云端 API Key、会话密钥和 TLS 路径等部署秘密。代码可以复制，秘密必须通过受控渠道为每台设备重新配置。
