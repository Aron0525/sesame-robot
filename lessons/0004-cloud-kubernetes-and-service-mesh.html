第四课 · 云原生拓扑

微服务、Kubernetes 与 Mesh

服务数量变多后，“一个入口”会分裂成外部入口、内部调用、客户端适配和集群路由。名字相似，职责却不同。

约 45 分钟31 个概念5 个练习
04—A

单体与微服务为什么需要不同网关策略

服务数量不是目的；边界、团队和发布方式才决定网关复杂度。

Concept 01

单体应用入口

一个应用进程承载大部分业务时，反向代理加应用中间件通常足够。

案例一个 FastAPI 服务同时处理用户、订单和聊天；Caddy 负责 HTTPS，FastAPI 负责登录与业务权限。
Concept 02

微服务 API Gateway

服务独立部署后，网关隐藏内部拓扑，并统一认证、配额、路由与版本。

案例客户端只调用 api.example.com，不直接知道 user-service、order-service 的内部地址。
Concept 03

External Gateway（外部网关）

面向公网用户或合作伙伴，重点是安全、API 契约、配额和外部身份。

案例合作伙伴通过 API Key 调用外部订单 API，但不能访问内部运维接口。
Concept 04

Internal Gateway（内部网关）

面向公司内部系统或服务，重点是服务身份、内部路由、审计和网络隔离。

案例财务系统通过内部网关调用订单结算接口，公网无法解析该域名。
判断“用了微服务”不代表必须上重量级 API 管理平台。如果调用方少、政策简单，Ingress Controller 或轻量代理仍可能足够。
04—B

BFF 与 API 聚合：别把通用网关变成超级后端

网关负责公共边界政策，BFF 负责某类前端的体验适配。

Concept 05

BFF（Backend for Frontend）

为某一种客户端提供专属后端接口，组合数据并适配交互需求。

案例小程序 BFF 一次返回订单、司机位置和联系电话；管理后台 BFF 返回统计和审计字段。
Concept 06

API Aggregation（API 聚合）

一次外部请求并行或串行调用多个内部服务，再组合响应。

案例“订单详情页”同时读取订单、用户、支付和司机服务。
Concept 07

Fan-out（扇出）

一个请求扩展为多个下游调用。扇出越大，任一依赖失败的概率和尾延迟通常越高。

案例一个页面并行调用 20 个服务，每个服务成功率 99.9%，整体全成功概率已经低于单个服务。
Concept 08

Backend Contract（后端契约）

BFF 可以稳定前端契约，但不能靠任意转换掩盖所有后端不兼容变化。

案例BFF 把内部多个状态映射成小程序需要的五种展示态，并对映射写契约测试。
反模式把支付计算、库存事务、Agent 工作流全部写进通用 API Gateway。结果是所有团队共用一个发布瓶颈，业务错误也会影响整个入口。
04—C

南北向与东西向流量

方向不是地理，而是系统边界的抽象。

Concept 09

North-South Traffic（南北向流量）

外部调用者与内部系统之间的流量，包括进入和出去。

案例手机调用订单 API 是进入；订单服务调用外部短信平台是出去。
Concept 10

East-West Traffic（东西向流量）

系统内部服务之间的通信。

案例订单服务调用支付服务和司机服务，属于东西向流量。
Concept 11

Ingress Gateway

控制流量进入集群或服务网格的入口。

案例公网 HTTPS 请求进入 Kubernetes 前先通过 Envoy Ingress Gateway。
Concept 12

Egress Gateway

控制内部服务访问外部系统的出口，便于固定出口 IP、审计、策略和密钥隔离。

案例所有模型调用统一从 Egress Gateway 出口，供应商只需放行一个固定 IP。
北：外部世界 │ Ingress Gateway │ 用户服务 ◀──── 东西向 ────▶ 订单服务 │ Egress Gateway │ 南：外部依赖
04—D

Kubernetes 中的入口对象

先分清 Kubernetes Service、Ingress 与 Gateway API。

Concept 13

Pod

Kubernetes 中承载一个或多个容器的基本运行单元，地址和生命周期可能变化。

案例订单服务部署三个 Pod；滚动更新时旧 Pod 消失、新 Pod 获得新 IP。
Concept 14

Service

为一组动态 Pod 提供稳定的访问身份和负载分发。

案例其他服务访问 order-service:8000，不必跟踪三个 Pod 的具体 IP。
Concept 15

Ingress

较早的 Kubernetes HTTP/HTTPS 入口 API，通过规则把外部流量路由到 Service。高级能力常依赖实现专属 Annotation。

案例/orders 指向 order-service，/users 指向 user-service。
Concept 16

Ingress Controller

监听 Ingress 等资源并实际配置代理或云负载均衡器的控制器。只有 Ingress YAML，没有 Controller，并不会自动产生流量入口。

通俗解释Ingress 是申请单，Controller 是读申请单并安排门卫和指示牌的人。
04—E

Kubernetes Gateway API 的完整资源模型

Gateway API 是一套标准化配置接口，不是某个具体网关产品。

Concept 17

GatewayClass

声明哪一种控制器和基础设施来实现一类 Gateway，通常由基础设施团队管理。

案例envoy-public 表示由某 Envoy Gateway 控制器实现公网入口。
Concept 18

Gateway

请求一个实际流量入口，声明地址、Listener 和使用的 GatewayClass。

案例平台团队创建 public-gateway，监听 80 和 443。
Concept 19

Listener

Gateway 接收流量的端口、协议、域名和 TLS 配置，也规定哪些 Route 可以附着。

案例443 Listener 只接受 *.example.com，并引用对应 TLS 证书。
Concept 20

HTTPRoute / GRPCRoute / TCPRoute

按协议描述匹配和转发规则。应用团队可独立管理自己的 Route。

案例订单团队的 HTTPRoute 把 /orders 附着到共享 Gateway。
Concept 21

BackendRef

Route 指向的后端对象，通常是 Kubernetes Service，也可由扩展支持其他目标。

案例HTTPRoute 的 BackendRef 指向 order-service:8000。
Concept 22

Role-oriented API（面向角色）

Gateway API 把基础设施提供者、集群运维者和应用开发者的职责分开。

案例平台团队管证书和公网地址；订单团队只管自己路径如何进入订单 Service。
基础设施团队 └─ GatewayClass：由谁实现 │ 平台团队 └─ Gateway + Listener：在哪里、用什么协议监听 │ 应用团队 └─ HTTPRoute：什么请求去哪里 │ Service │ Pods
核心区别API Gateway 是一种架构组件或产品；Kubernetes Gateway API 是描述服务网络入口与路由的资源标准。一些 API Gateway 产品可以实现 Gateway API，但二者不是同义词。
04—F

Service Mesh：把网关能力铺到服务之间

API Gateway 主要守入口；Service Mesh 主要治理内部调用。

Concept 23

Service Mesh（服务网格）

用基础设施代理统一处理服务间身份、mTLS、流量策略与观测，尽量不让业务代码重复实现。

案例订单服务无须自己写证书轮换，就能与支付服务建立 mTLS。
Concept 24

Sidecar Proxy（边车代理）

每个工作负载旁运行一个代理，应用进出流量经过它。

通俗解释每家店门口都配一名统一培训的保安，而不是只在商场总门口安排保安。
Concept 25

Ambient / Node Proxy（环境式或节点代理）

不为每个 Pod 单独部署完整 Sidecar，而在节点或共享层拦截流量，减少资源和注入复杂度。

案例同一节点上的多个服务共享基础四层安全代理，七层能力按需增加。
Concept 26

Workload Identity（工作负载身份）

为服务实例提供可验证身份，而不是依赖易变化的 IP。

案例只允许身份为 order-service 的工作负载调用 payment-service。
Concept 27

Zero Trust（零信任）

不因为流量来自内网就自动信任；每次通信都验证身份、权限和上下文。

案例即使攻击者进入集群网络，没有合法工作负载证书也无法调用支付服务。
Concept 28

Mesh Control Plane

向大量代理分发服务发现、证书和流量政策；代理构成数据面。

案例控制面下发“订单 v2 接 5% 流量”，所有相关代理执行一致规则。
04—G

不同协议对网关提出不同要求

不能用普通短请求的默认值处理所有通信。

Concept 29

REST / HTTP

请求—响应模型清晰，适合路径路由、缓存和常规认证。

案例GET /orders/123 可按 HTTP 方法和资源路径路由。
Concept 30

gRPC

基于 HTTP/2 和 Protobuf，支持流式调用；网关需要理解服务/方法、HTTP/2 与 gRPC 状态。

案例外部调用 OrderService/GetOrder，网关按 gRPC 方法分流。
Concept 31

WebSocket 与 SSE

WebSocket 是长连接双向通信；SSE 是服务器到客户端的单向流。超时、连接数、负载均衡和部署摘流必须单独设计。

案例LLM 流式输出使用 SSE，网关不能沿用普通 API 的 5 秒总超时。
Concept 32

TCP / UDP Gateway

对数据库、自定义协议、游戏或 DNS 等非 HTTP 流量进行四层转发。

案例TCP Gateway 把 PostgreSQL 连接送到主库或只读库入口，但不理解 SQL 业务含义。
Related Concept

Message / Event Gateway（消息或事件网关）

在外部生产者与内部消息系统之间处理协议适配、身份、主题映射和流量控制。它与同步 API Gateway 类似，但处理的是消息发布/订阅语义。

案例IoT 设备通过 MQTT Gateway 发布传感器事件，网关验证设备证书后映射到 Kafka Topic。
04—H

常见部署拓扑

没有一个“标准网关图”适合所有规模。

拓扑适合代价案例
单入口网关小型系统、政策统一故障域与发布耦合较大一个 Nginx 前接一个 FastAPI 单体
边缘网关 + BFF多客户端体验差异大多一层服务与契约小程序和管理后台各有 BFF
外部网关 + 内部网关内外安全边界明确政策协调更复杂伙伴 API 与公司内部 API 分离
Ingress + Service Mesh服务多、内部治理要求高资源和运维复杂度高Kubernetes 中入口 Envoy 加内部 Mesh
全局网关 + 区域网关多区域、全球用户数据一致性与跨区故障复杂全球流量先选区域，再进区域网关
04—I

检索练习

把相似概念放在一起比较。

1. BFF 与 API Gateway 的主要边界是什么？

API Gateway 负责跨服务公共入口政策；BFF 负责某类前端的数据组合和体验适配。

2. Kubernetes Ingress YAML 为什么不能单独转发流量？

它是期望状态声明，需要 Ingress Controller 读取并配置真实代理或负载均衡器。

3. GatewayClass、Gateway、HTTPRoute 分别是谁管什么？

GatewayClass 定义实现类型；Gateway 定义入口和监听；HTTPRoute 定义具体请求如何去后端。

4. API Gateway 和 Service Mesh 的主要流量方向差别是什么？

API Gateway 多治理外部到应用的南北向入口；Service Mesh 多治理内部服务之间的东西向通信。

5. 为什么 LLM 流式响应不能照搬普通 REST 超时？

流式连接可能持续很久，但仍在不断传输数据，需要区分总超时与空闲超时，并正确处理连接排空。
