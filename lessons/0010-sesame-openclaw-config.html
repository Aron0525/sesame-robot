Sesame Robot · OpenClaw 配置

API 只解决“模型能调用”

要让 OpenClaw 进入机器人产品，还要配置身份边界、会话、结构化输出、沙盒、工具权限、记忆和运行维护。对 Sesame 来说，安全边界比增加工具更优先。

约 10 分钟基于本机实测先隔离再接入

10—B

除了 API，还要配置七层

每一层解决的是不同问题，不能互相替代。

01 · Gateway

连接与鉴权

固定本机端口、loopback 绑定和 gateway token。Voice Gateway 通过本机连接 OpenClaw；Wi-Fi、mDNS 和 ESP32 配对不属于 OpenClaw。

02 · Agent

专用角色

建立 sesame Agent，使用独立 workspace、系统提示词和模型参数，不复用拥有个人工具的 main。

03 · Session

会话隔离

由 user_id + device_id 生成稳定 session key，并明确超时、清理和并发规则，防止不同设备串上下文。

04 · Contract

固定 JSON 契约

回答、动作和表情必须符合版本化 Schema；OpenClaw 只返回意图，Voice Gateway 再验证和下发。

05 · Sandbox

运行位置隔离

决定工具是在宿主机还是隔离容器中运行。Sesame 应使用 all 模式，scope 至少为 agent，更严格时用 session。

06 · Tool policy

能力最小化

决定 Agent 能调用哪些工具。首版语音问答不需要 shell、文件系统、浏览器、定时任务、节点控制或 Gateway 管理工具。

07 · Operations

记忆、日志和运行维护

首版关闭长期记忆或只保存脱敏的最少文本；设置模型超时、错误事件、健康检查、自动重启和延迟指标。原始 Opus、PCM、Wi-Fi 密码与 token 不进入模型上下文。

10—C

沙盒和工具权限要同时配置

这是 OpenClaw 最容易混淆、也最关键的部分。

Sandbox（沙盒） 决定：工具代码在哪里执行 目标：即使工具出错，也尽量不影响宿主机 Tool policy（工具策略） 决定：模型能不能调用某个工具 目标：模型根本看不到不需要的能力 Elevated（提权执行） 决定：exec 是否可以绕出沙盒到宿主机 Sesame：关闭
不能只禁用 write/edit如果仍允许 exec，shell 命令照样可以修改或删除文件。官方策略中 deny 优先；使用 allowlist 时，未列出的工具都应视为不可用。
Sesame 第一版建议值原因
Sandbox modeall包括主会话在内的工具执行全部隔离
Sandbox scopeagent；多用户时优先 session避免不同角色或用户共享容器边界
Workspace accessnone纯语音问答不需要读取电脑文件
Tool allowlist首版为空或只保留纯文本所需能力OpenClaw 只负责推理和结构化回答
Elevatedfalse不允许机器人语音入口执行宿主机命令
10—D

OpenClaw 只输出“意图”，不直接控制硬件

动作安全由确定性程序负责，不能交给模型自由发挥。

ASR 文本 + user_id + device_id ↓ Voice Gateway：构造受控请求 ↓ OpenClaw sesame Agent：只做理解与决策 ↓ 固定 JSON：reply_text / actions / expressions ↓ Voice Gateway：Schema、枚举、范围、deadline 再验证 ↓ TTS 文本 + ESP32 白名单动作
{
  "version": "1.0",
  "reply_text": "你好，我在这里。",
  "actions": [
    {"name": "wave", "duration_ms": 1200}
  ],
  "expressions": [
    {"name": "happy", "duration_ms": 1800}
  ]
}

如果输出不合规，Voice Gateway 最多发起一次受限修复；仍失败就返回 agent.error。ESP32 只执行固件白名单内、参数合法且未过期的动作。

10—E

你的配置顺序

顺序本身也是风险控制：先建立边界，再开放能力。

  1. 保留当前 127.0.0.1:18789 + token，不把 OpenClaw Gateway 暴露给 ESP32；ESP32 只连接 Voice Gateway。
  2. 创建独立 sesame Agent 和 workspace，把 Sesame session key 从 agent:main:sesame:... 改到专用 Agent。
  3. 对该 Agent 开启 Sandbox，关闭 elevated，并设置最小工具 allowlist。
  4. 写入专用系统提示词：固定语言、回答长度、动作/表情枚举和严格 JSON Schema。
  5. 配置模型超时、最大输出、并发数、会话清理；首版关闭长期记忆。
  6. 让 Voice Gateway 完成 Schema 校验、一次修复、错误映射、日志脱敏和延迟统计。
  7. 最后再逐个增加窄工具，例如只接受枚举参数的 robot_action；不要开放 shell 或直接 GPIO 控制。
多用户边界Session key 只负责上下文路由，不是权限边界。一个家庭内的多台设备可以在同一租户 Gateway 中使用不同 session；互不信任的不同客户不能共用一个 OpenClaw Gateway。产品化部署应按用户或家庭建立独立 Gateway cell、凭据和状态目录，最好再使用独立容器、OS 用户或主机。
10—F

配置完成后的验收命令

不要只看配置文件，要看最终生效策略。

openclaw doctor
openclaw security audit --deep
openclaw sandbox explain --agent sesame --json
openclaw gateway probe
  • sandbox explain 必须显示 Sesame 会话已 sandboxed。
  • 有效工具中不得出现 exec/process/read/write/edit/apply_patch 等宿主机能力。
  • 用恶意 ASR 文本测试“读取文件、执行命令、修改配置”，应全部被拒绝。
  • 用错误动作名、超长时长和错误 JSON 测试，Voice Gateway 应拒绝并产生明确错误。
  • 修复当前 nvm Node 的 LaunchAgent 警告，重启电脑后 Gateway 仍应自动可用。

10—H

一分钟自测

能回答这三个问题，说明边界已经清楚。

配置了 API，为什么还不能直接给用户使用？

API 只让模型可调用，并没有限制会话身份、工具权限、文件访问、命令执行和硬件动作。当前 Sesame 会话甚至还是未沙盒化状态。

有 Sandbox 后，是否可以允许所有工具？

不可以。Sandbox 只缩小事故影响范围，tool policy 才决定模型能否调用工具。两层必须同时使用。

OpenClaw 是否应该直接操作舵机？

首版不应该。它只输出经过 Schema 约束的动作意图，Voice Gateway 与 ESP32 再通过白名单、范围和 deadline 做确定性验证。
