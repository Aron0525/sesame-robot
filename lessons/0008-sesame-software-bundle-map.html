六个目录，一条运行链路

目录不是六套互不相关的程序：Arduino 在机器人端，Voice Gateway 在电脑端居中，ASR/TTS 与 OpenClaw 被它调用，协议文件约束双方，Sesame Studio 负责生成动作代码。

08—A

先看完整链路

每个目录都对应链路中的一个职责。

01 Arduino 固件（ESP32-S3） │ WebSocket：JSON 控制事件 + Opus 音频 ▼ 02 Voice Gateway（FastAPI） ├─→ 03 ASR：PCM → 文字 ├─→ 04 OpenClaw：文字 → 回答 / 工具调用 └─→ 03 TTS：回答文字 → PCM │ └─→ 01 Arduino：Opus 音频 + 动作/表情 05 配置与协议：约束上述消息和环境变量 06 Sesame Studio：生成动作序列，最终放入 Arduino 固件
中心组件Voice Gateway 是软件链路的编排中心。ASR、TTS 和 OpenClaw 不直接与 ESP32 交换音频。

第一次使用：只跑电脑 Demo

暂时不接真实 ESP32、ASR/TTS 或 OpenClaw，先证明中间链路可运行。

终端一： cd 02-Voice-Gateway/SesameRobot cp .env.example .env uv sync --python 3.12 uv run uvicorn sesame_voice_gateway.app:app \ --app-dir apps/voice_gateway/src \ --host 0.0.0.0 --port 8765 终端二： uv run python apps/esp32_simulator/simulate.py \ --url ws://127.0.0.1:8765/v1/device-stream \ --gateway-id gw_local_dev \ --device-id dev_001 \ --token '<与 .env 一致>'
这一步验证什么WebSocket、设备鉴权、JSON/Opus 协议、流水线和返回音频；不验证真实语音模型。
08—E

正确的推进顺序

一次只增加一个真实组件，出错时才知道问题在哪一层。

阶段 1：Arduino 固件能编译、上传，串口稳定 阶段 2：电脑 Demo 闭环通过 阶段 3：Voice Gateway 接入真实 OpenClaw 阶段 4：接入真实 ASR Provider 阶段 5：接入真实 TTS Provider 阶段 6：真实 ESP32 麦克风/扬声器接入 阶段 7：Sesame Studio 生成动作并做整机验收
反例同时接真实 ESP32、ASR、TTS 和 OpenClaw。一旦没有声音，无法判断是采集、编解码、网络、模型、Agent 还是播放问题。
08—F

一分钟自测

先在脑中回答，再展开答案。

哪个程序是整条语音链路的中心？

Voice Gateway。它接收 ESP32 音频，调用 ASR、OpenClaw 和 TTS，再把结果送回 ESP32。

ASR 能不能直接接收 Opus？

当前设计不能。Voice Gateway 先把 Opus 解码成 PCM，ASR Provider 只接收 PCM。

现在能否声称真实 ASR/TTS 已完成？

不能。当前只有 Provider 接口和 Demo 实现，真实模型尚未接入。
