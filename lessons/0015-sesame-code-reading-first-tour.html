15—A

先从入口，而不是目录，开始

打开 firmware/esp32_voice_idf/main/app_main.cpp。

这个文件没有实现“机器人如何听懂话”。它只创建对象并连接依赖：

AudioHal audio = I2S 音频硬件 Esp32ServoDriver robot_driver = PWM 舵机硬件 OledExpressionDisplay display = I²C 表情硬件 LegacyMotionRunner legacy = 旧动作表兼容层 RobotAdapter robot = 统一机器人操作入口 WebControlServer web_control = 设备本地 HTTP 控制 VoiceController voice = 语音总调度器
正确的提问方式看到 VoiceController voice(&audio, &robot)，先问“它拿到了哪些能力？”答案：能读写声音，也能请求安全急停/表情/本地动作；但没有 DashScope Key、OpenClaw Token 或浏览器权限。
15—B

按 BOOT 后，第一步不是发音频

按键逻辑在 recording_button.cpp，主处理在 VoiceController::run()。

  1. 主循环读取 GPIO0，低电平表示按下。
  2. RecordingButton::update() 用 80 ms 去抖，且要求先有一次稳定释放；复位时按住 BOOT 不会误触发。
  3. handle_button() 只在 session_ready_ 时工作：还没与 Gateway 成功握手的设备不会产生无归属录音。
  4. 已有录音则 finish_listening()；否则 start_listening(..., CaptureSource::kManual)。

所以 BOOT 是一次语音回合的开始/结束触发器，不直接碰 Opus、WebSocket 或模型。

15—C

start_listening()：不是“开麦”，而是建立可追踪回合

它在真正采样前完成身份、状态和打断处理。

动作代码意图为什么必要
检查前提必须已经 session.ready、没有 active capture、来源合法。避免嵌套录音。
打断旧回复若正在 Thinking/Speaking，先发 interrupt、清播放、急停。新用户输入优先，旧 TTS 不应继续。
创建 turn ID计数器加一，组合随机数生成独特 ID。把每帧音频与一轮业务严格关联。
重置 codec/序号codec_.reset()，audio_sequence_=0。前一轮的编码状态和包号不能泄入新回合。
先发 listen.start告诉 Gateway 当前 trigger 是 manual/wakeword/followup。Gateway 只有在这个控制事件后才接受 binary uplink。
15—D

一帧声音如何变成网络包

关键文件：audio_hal.cpp、opus_codec.cpp、voice_controller.cpp。

INMP441 24-bit 数据在 32-bit I2S 槽内 ↓ AudioHal::read_microphone_frame() 320 个 int16 PCM（20 ms / 640 bytes） ↓ OpusCodec::encode() 变长 Opus packet（最多 1500 bytes） ↓ protocol::pack_audio_frame() 32-byte SSM1 header + Opus payload ↓ enqueue_outbound_binary() sesame_uplink 任务 → GatewayClient::send_binary() → WSS

请区分两种“帧”：PCM 帧固定是 20 ms / 320 samples；Opus 包是可变长度。SSM1 头额外说明它属于上行、哪一轮、这一轮的第几个包。

为什么要把发送独立为任务capture_and_send() 只做快速编码与入队；真正的 TLS/WSS send 在 sesame_uplink 任务中完成。网络慢不会阻塞 I2S 采样。
15—E

Gateway 收到后，先验证，后处理

依次看 app.py::_authenticate_session、_receive_audio、_run_turn。

  1. 第一帧必须是 session.hello，且控制序号为 0。
  2. Gateway 比对 gateway_id、Bearer token、设备到用户的映射，并拒绝同一设备的第二条活跃连接。
  3. 二进制包必须为 uplink、stream ID=1、Opus flags=0、generation 非 0、序号连续，且最多 1,500 包/30 秒。
  4. listen.stop 后才创建异步 _run_turn；接收循环仍在运行，因此用户能随时 interrupt。

DeviceSession 不是数据库用户

它是一条在线 WSS 连接的内存状态：保存音频包、序号、当前异步任务、turn_epoch 和 send_lock。中断时 epoch 加一并取消旧 task；迟到的旧 task 因 epoch 不匹配而不能再发 TTS。

15—F

Pipeline：一轮业务的五步

ConversationPipeline.process_turn() 等待云端时不会阻塞其他设备收帧。

阶段输入输出失败时
Opus decode本轮 packet 列表连续 PCM失败，不下发半截声音。
Privacy + ASRPCM转写文本超 30 秒拒绝；无声/无效文本返回 SilentDiscard，不调用 Agent。
OpenClaw文本与关联 ID严格 JSON AgentResult超时/格式错误发送通用 error，不泄露用户内容。
TTS通过校验的回复文字16 kHz PCM空 PCM 或非完整帧立即失败。
Opus encodeTTS PCM下行 packets + generation编码失败则不会开始播放。
15—G

回复如何安全回到 ESP32

_send_turn_result() 不是一次把所有字节塞进网络。

response.plan（表情、generation；当前 action 始终 null） ↓ tts.start（generation_id） ↓ 每 20 ms 一包 SSM1 DOWNLINK，stream_id=2，sequence=0,1,2... ↓ tts.stop（同一 generation） ↓ ESP32 begin_tts() → 按序 Opus decode → I2S write → 队列排空后关功放 ↓ 等待约 3 秒 follow-up；超时后重新等唤醒词
generation 的意义用户在旧回复未播完时再次按 BOOT，固件会 interrupt 和清下行队列；Gateway 取消旧 task。迟到的旧 generation 包会被过滤，不能混入下一句回复。
15—H

读完后应能回答的四件事

答不上来就回到函数，不要急着继续浏览新目录。

为什么 session.ready 前不接受 BOOT 录音？

设备还没有合法会话、认证后的 conversation 和双方确认的音频协议；上传音频无法安全归属。

为什么 sequence 和 generation 都要检查？

sequence 检测同一回合内丢包/重复/乱序；generation 区分不同回合。只检查一个无法防止旧回复迟到。

当前 AI 为什么不能控制舵机？

OpenClaw 适配层将 actions 清空，Gateway 下发前又设 action 为 None。网页操作员控制使用独立的 operator.control 通道。

DashScope Key 应在哪一层？

只在电脑 Gateway 的 .env。ESP32 与 OpenClaw 都不应拥有它。
