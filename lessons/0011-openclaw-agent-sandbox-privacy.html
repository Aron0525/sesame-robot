Sesame Robot · 系统边界

不是必须用这台电脑，
而是必须有一台运行主机

ESP32 负责实时音频和硬件，Voice Gateway 负责语音协议与安全验证，OpenClaw 负责对话决策。三层可以一起迁移到新的边缘主机或服务器，但不应把 OpenClaw 控制面直接暴露给 ESP32。

约 16 分钟基于 OpenClaw 2026.7.1-1含固定契约
11—A

可迁移的部署单元

“本机”只是当前部署位置，不是架构限制。

ESP32-S3 │ WSS：Opus + 设备控制事件 ▼ Voice Gateway（必须） ├─ Opus 解码 / 编码 ├─ ASR / TTS 调度 ├─ 设备认证、限流、Schema 和动作白名单 └─ 只把 ASR 文本交给 OpenClaw │ 本机 loopback WebSocket ▼ OpenClaw Gateway └─ sesame Agent → 模型 API 或本地模型
部署位置适用场景判断
当前 Mac开发和单机验证最快，但电脑必须在线
家庭迷你主机 / 边缘盒子每个家庭一套产品隐私和延迟最好，推荐产品路线
云服务器集中运维和远程设备需要公网 WSS、租户隔离和更高成本

迁移时移动什么

迁移 Voice Gateway、ASR/TTS 运行时、OpenClaw Gateway、sesame workspace、配置和必要凭据。ESP32 只需要换成新 Voice Gateway 的域名或配对信息。

11—B

ESP32 能否直接连接 OpenClaw

协议上可以开发客户端，产品上不应该这样连接。

OpenClaw Gateway 使用 WebSocket 文本帧和 JSON。客户端要实现协议版本协商、challenge 签名、设备身份、配对、token、role、scope、重连和事件顺序。ESP32 理论上可以实现这些，但 OpenClaw Gateway 是控制面，不是 Opus 音频流服务器。

直接连接的问题： Opus 二进制流 ≠ OpenClaw 的 JSON 控制协议 设备固件会绑定 OpenClaw 的协议版本 ESP32 会接触高权限 Gateway token / scope ASR、TTS、动作校验和限流仍然没有位置 OpenClaw 升级可能迫使全部设备固件升级
结论ESP32 只实现稳定的 Sesame Voice Protocol；Voice Gateway 作为 OpenClaw Adapter。这样迁移主机或替换 Agent 框架时，ESP32 固件不需要改变。
11—C

Agent、main 和 workspace

Agent 是一套“逻辑大脑配置”，不是另一个模型。

名词真正含义Sesame 中的作用
Agent模型、提示词、workspace、记忆、session store 和工具权限的组合边界把机器人和个人助理分开
main Agent未配置多 Agent 时自动创建的默认 Agent ID当前微信和 Sesame 都进入这里，容易混上下文与权限
main session某个 Agent 的根会话，例如 agent:main:main与 main Agent 不是同一个概念
workspaceAgent 的提示文件和工作目录保存机器人的规则、角色和可用资产说明

sesame workspace 中的 AGENTS.md 定义操作规则，SOUL.md 定义语气和边界，IDENTITY.md 定义身份，USER.md 定义最少用户偏好。它们会进入系统上下文，因此不能存 API Key、Wi-Fi 密码或用户原始音频。

为什么必须单独建 sesame Agent

它能独立限制工具、关闭记忆、固定模型和输出风格，避免个人助理的邮件、文件和聊天记忆进入机器人回答，也避免机器人用户通过提示注入碰到个人电脑能力。

11—D

Session key 是路由键，不是密码

同一段对话复用 Key，新对话才创建新的 session_id。

agent:sesame :user:u_7f92 ← 假名化 UserID，不用手机号 :device:d_a31c ← 物理产品 DeviceID :session:s_20260726 ← 一段连续对话 每句话只更换： turn_id / request_id 开启新对话才更换： session_id
  • UserID 防止甲用户的历史进入乙用户。
  • DeviceID 确定回答和动作应该回到哪一台机器人。
  • SessionID 限制对话上下文寿命，防止永久累积。
  • TurnID 和 RequestID 用于去重、重试和链路追踪。
安全边界知道 session key 不代表拥有访问权限。不同、不互相信任的客户不能只靠不同 session 共用一个 Gateway。OpenClaw 官方要求多租户按客户拆分 Gateway、凭据，最好再拆分 OS 用户、容器或主机。
11—E

固定输入和输出契约

OpenClaw 只处理文字和允许能力，不接收 Opus、PCM 或设备秘密。

Voice Gateway → OpenClaw

{
  "v": 1,
  "request_id": "req_001",
  "device_id": "dev_001",
  "user_id": "usr_001",
  "session_id": "ses_001",
  "turn_id": "turn_001",
  "input": {"type": "text", "text": "和我挥手打招呼"},
  "capabilities": {
    "actions": ["wave", "stand", "rest", "stop"],
    "expressions": ["default", "happy", "thinking"]
  }
}

OpenClaw → Voice Gateway

{
  "v": 1,
  "request_id": "req_001",
  "turn_id": "turn_001",
  "status": "completed",
  "reply": {"text": "你好，很高兴见到你。"},
  "voice": {
    "voice_id": "sesame_default",
    "style": "happy",

  },
  "expression": {"name": "happy", "ttl_ms": 2500},

}

Voice Gateway 必须再次用 JSON Schema、动作枚举、范围和 deadline 校验。模型输出不是授权；ESP32 固件白名单才是最后执行边界。

11—F

Sandbox 到底隔离什么

OpenClaw 的默认后端是 Docker，Gateway 留在主机，工具进入隔离容器。

隔离对象具体效果不是绝对保证
文件系统容器看不到主机目录，除非显式挂载workspaceAccess: rw 或 bind mount 会打洞
进程shell 和子进程运行在容器命名空间Gateway 自身仍运行在主机
网络Docker 默认 network: none启用网络后仍需目的地白名单
系统权限默认只读 root、drop capabilities挂载 Docker socket 等同交出主机控制权
资源可限制 CPU、内存、PID需要显式配置和监控
Sandbox 不是全部它不隔离模型服务商看到的文本，也不保护已泄漏的 Gateway token；更不能替代每客户独立 Gateway。它只缩小工具执行造成的主机影响范围。

本机 Docker 已运行，但当前没有 openclaw-sandbox:bookworm-slim 镜像，所以仅写配置还不能真正启用。需要先按官方文档构建镜像，再添加 per-agent sandbox 配置。

11—G

Tool Policy 是硬权限表

提示词说“不要执行命令”是软规则；Tool Policy 让模型根本看不到该工具。

工具是否到达模型： Profile 基础集合 → Provider 限制 → Agent allow / deny → Sandbox 工具策略 → Sender 限制 → 最终可见工具 规则： deny 永远获胜 allow 非空时，未列出的工具全部阻止

Sesame 首版只需要生成结构化回答，不需要任何动作工具。使用 minimal profile，并禁止 runtime、filesystem、session、memory、web、UI、automation、messaging、nodes、agents、media 和 plugin 工具；同时关闭 elevated 和 exec。

以后增加工具不要开放 exec。应设计窄工具，例如 get_weather(city)；机器人动作仍建议作为受约束 JSON 意图，由 Voice Gateway 和 ESP32 白名单执行。
11—H

训练、记忆和隐私是三件事

创建 Agent 不是训练模型，保存 Session 也不等于模型训练。

概念发生了什么你的首版选择
提示词配置每次请求把规则交给模型需要；不改变模型权重
SessionOpenClaw 在本地保存对话记录短期保留并定期删除
Memory把信息整理或索引后跨会话召回关闭跨会话记忆和 transcript indexing
模型训练 / 微调改变模型权重MVP 不需要；用户数据不得默认用于训练
模型 APIASR 文本和系统上下文发送到供应商按供应商数据政策处理；高隐私场景用本地模型
数据最小化路径： 原始音频 → 只在 Voice Gateway / 本地 ASR 短暂停留 ASR 文本 → 删除姓名、电话、地址等不必要字段 OpenClaw → 只接收文本、假名 ID、允许动作列表 模型 API → 只发送回答所需内容 TTS → 只接收 reply.text 和 voice_id 日志 → 只记耗时、错误码、哈希化 request_id
  • 如果 ASR/TTS 改用云 API，音频或合成文本会离开本机，必须单独告知用户。
  • 关闭 OpenTelemetry 内容采集；不要启用 diagnostics.otel.captureContent。
  • 开启日志敏感值脱敏，并为 Wi-Fi、设备 token、VoiceID 增加项目正则。
  • Session 数据设置保留期和删除入口；磁盘启用 FileVault 或服务器磁盘加密。
  • 声音克隆必须取得声音所有者明确授权，并支持撤回、删除和重新注册。
11—I

实施顺序

本课只定义目标配置，没有修改当前 OpenClaw。

  1. 运行 openclaw agents add sesame --workspace ~/.openclaw/workspace-sesame。
  2. 填充专用 AGENTS.md、SOUL.md、IDENTITY.md，固定回答和 JSON 规则。
  3. 构建官方 Sandbox Docker 镜像。
  4. 在 agents.list[] 为 sesame 写入 mode: all、scope: session、workspaceAccess: none 和最小 Tool Policy。
  5. 运行 openclaw config validate 和 openclaw sandbox recreate --agent sesame。
  6. 发起一次 Sesame 对话，再用 openclaw sandbox explain --agent sesame --json 验证生效边界。

完成标准

Sesame 会话显示 sandboxed；工具列表没有 shell、文件、浏览器、消息和节点控制；模型只返回项目 Schema；恶意语音文本不能读取主机文件或调用未授权能力。

11—K

一分钟自测

先回答，再展开。

ESP32 为什么不直接把 Opus 发给 OpenClaw？

OpenClaw Gateway 是 JSON 控制面，不是 Opus 音频流服务器；Voice Gateway 还承担编解码、ASR/TTS、认证、限流和动作安全校验。

Session key 为什么不是多用户安全边界？

它只选择上下文桶，不证明调用者身份。互不信任的客户需要不同 Gateway cell 和凭据。

Sandbox 和 Tool Policy 哪个更重要？

两者都需要。Tool Policy 先阻止能力出现，Sandbox 再限制漏网或后来开放的工具对主机造成的影响。
