ASR/TTS 的封装是什么意思

先把 ASR/TTS 定义成独立能力，再分别适配本地模型和远程 API。调用方不需要知道能力究竟运行在哪里。

约 15 分钟本地与远程统一 Provider
S—A

先建立“封装”的心智模型

调用方只需要知道怎样使用能力，不需要知道模型内部怎样加载、推理和后处理。

VoiceSession ├─ AsrProvider │ ├─ LocalAsrProvider → 本机 sherpa/FunASR 模型 │ └─ RemoteAsrProvider → 云厂商 ASR API └─ TtsProvider ├─ LocalTtsProvider → 本机 Kokoro/CosyVoice 模型 └─ RemoteTtsProvider → 云厂商 TTS API
Core idea

封装隐藏“怎么做”

本地模型的文件路径、推理框架和 CPU/GPU，以及远程 API 的鉴权、URL 和厂商格式，都留在各自适配器内部。

案例上层只调用 synthesize(text)，不用知道底层是本机 Kokoro 还是云端 TTS API。
Contract

封装公开“怎样用”

输入、输出、错误、超时、取消、并发和健康状态必须形成明确契约。

反例只写一个 run_model()，却不定义音频格式、取消方式和错误类型，这只是藏代码，不是可靠封装。
S—B

封装有四层，不要混为一谈

一套系统可以同时使用四层；它们回答的是不同问题。

层次回答的问题ASR/TTS 例子
代码封装上层调用什么接口？AsrProvider、TtsProvider
进程封装模型和网关是否共享进程？ASR worker、TTS worker
服务封装进程之间用什么协议？HTTP、WebSocket、gRPC
部署封装怎样安装、启动和隔离？venv、systemd、Docker、Compose
关键判断“封装成 API”属于服务封装；“封装成 Docker”属于部署封装。Docker 不会自动替你设计一个正确的 API。
S—C

两种来源，都必须封装

差别在于封装内部负责的事情不同，对 Voice Gateway 暴露的能力契约应尽量相同。

维度本地模型封装远程 API 封装
推理位置端侧电脑 CPU/GPU厂商服务器
封装重点加载模型、硬件、线程、内存、音频前后处理鉴权、请求转换、响应转换、限流、重试、网络错误
网络可完全离线；进程内或本机通信依赖互联网和厂商可用性
隐私音频不必离开本机音频或文本会发送给厂商
成本购买硬件和承担本地运维通常按时长、字符或请求计费
扩容自己管理并发和硬件容量厂商负责模型容量，但受配额限制
典型故障内存不足、模型加载失败、推理过慢超时、断网、429、鉴权失败、厂商故障
统一边界两种实现最终都应转换成项目自己的 AsrEvent 和 PCM chunk，而不是让厂商 JSON 或本地模型 tensor 泄漏到 VoiceSession。
S—D

本地模型内部还能怎样封装

本地与远程是能力来源；同进程、worker、服务和容器是本地实现的部署形式。

Method 01

同进程 Python 类

FastAPI 直接创建模型对象，通过 Provider 类调用。

适用单模型原型、短期验证。
代价推理阻塞、依赖冲突或模型崩溃会拖垮 Voice Gateway。
Method 02

独立 worker 进程

ASR/TTS 分别常驻在本机进程，通过 Queue、Pipe 或 Unix domain socket 通信。

适用单机 MVP，既要隔离又不想先维护网络服务。
Method 03

本地模型服务

ASR/TTS 各自提供 HTTP、WebSocket 或 gRPC API，Gateway 作为客户端。

适用正式项目、模型可替换、以后可能迁移 GPU 主机。
Method 04

Docker 容器

把依赖、模型服务和启动方式打入镜像，再用 Compose 编排。

适用Linux/NVIDIA 生产部署和多服务交付。
反例在 Apple Silicon 上为了“看起来正式”先套不兼容的 x86/CUDA 镜像，反而失去本机加速并增加排错成本。
Method 05

本地守护进程或原生库

用 systemd/launchd 管理常驻服务，或者把 ONNX/C++ runtime 通过 FFI（外部函数接口）暴露给 Python。

适用追求最低 IPC 开销、桌面产品化或需要开机自启。实现和维护成本最高，不应作为第一版起点。
S—E

为什么需要封装

目的不是隐藏几行代码，而是把变化和故障限制在 ASR/TTS 边界内。

不封装的风险在语音系统里的具体后果封装怎样控制
模型耦合从云 ASR 换到本地 ASR，需要修改 WebSocket、会话和 Agent 链路只替换 Provider Adapter
格式泄漏24 kHz WAV、16 kHz PCM、Opus 和厂商 JSON 在业务层混用Provider 统一输出项目 PCM/Event
资源失控每个连接重复加载本地模型，导致内存耗尽或阻塞事件循环统一管理模型生命周期和并发
打断失效用户已经说话，旧 TTS 仍继续生成和播放统一 cancel 与 generation_id
故障扩散超时、429、断网或模型崩溃直接破坏整条会话适配器转换错误并执行明确策略
安全泄漏API Key 散落在业务代码，或本地失败后擅自把音频传到云端密钥与隐私策略集中在 Provider
无法测试每次测试都必须启动真实模型或付费云 APIFake Provider 可稳定模拟事件与故障
封装顺序： 1. 定义项目自己的 AsrProvider / TtsProvider 契约 2. 定义统一 AsrEvent、PCM 格式、错误和取消语义 3. 实现 Local Adapter 与 Cloud Adapter 4. 用 Factory/Dependency Injection 按配置选择实现 5. 为 Provider 写独立 contract tests 6. 最后决定本地实现是同进程、worker、服务还是 Docker
最低必要封装正式项目至少完成“统一接口 + Local/Cloud Adapter + 统一格式/错误/取消 + 可替换配置”。独立进程、API 服务和 Docker 不必第一天全部完成。
S—F

云端 API 还需要本地算力吗

模型推理算力由厂商承担，但本地仍要处理音频、网络和设备协议。

云端 ASR： ESP32 Opus → 本地解码/重采样/发送 → 云端模型推理 → 本地接收文本 云端 TTS： 本地发送文本 → 云端模型推理 → 本地接收音频/解码/重采样/Opus 编码 → ESP32
Cloud compute

云端负责的重计算

神经网络前向推理、模型权重、显存和模型并发容量都在厂商服务器。本地不需要为了该云模型准备 GPU 或下载权重。

Local compute

本地仍然负责什么

麦克风采集、Opus/PCM 编解码、VAD、AEC、降噪、重采样、加密传输、JSON 解析、队列、打断和扬声器播放仍会使用本地 CPU、内存与网络。

结论云端 API 不需要本地“模型算力”，但需要本地“系统处理算力”。后者通常远小于运行 ASR/TTS 神经网络所需的算力。
S—G

封装能保护 API 和隐私吗

能帮助集中控制，但只有和安全机制组合后才真正有效。

错误： ESP32 / 前端 App ── 内置永久 API Key ──→ 云厂商 正确： ESP32 ── 设备短期凭证/WSS ──→ Voice Gateway ├─ Secret Manager 中的厂商密钥 ├─ Cloud Provider Adapter ├─ 音频外发策略 └─ 日志脱敏与审计 ↓ 云 ASR/TTS
目标封装提供什么还必须增加什么
保护 API Key所有厂商调用集中在 Cloud Adapter后端代理、Secret Manager、轮换、最小权限
保护用户音频统一控制哪些数据可以外发TLS、用户同意、数据最小化、保留/删除政策
防止日志泄漏统一事件和错误出口日志脱敏、禁止记录原始音频/完整对话/密钥
本地失败回退所有切换经过 Provider Factory/Policy禁止未经授权自动回退到云端
API security

先保护入口

认证确认“你是谁”，授权决定“你能访问谁的数据”，TLS 防止传输窃听，签名/防重放保证请求未被伪造，限流降低批量盗取和资源耗尽风险。

Data protection

再保护数据生命周期

即使请求合法，也要限制收集内容、租户隔离、静态加密、日志脱敏、云端外发、保留期限、备份和删除。合法用户不等于可以读取所有用户数据。

重要限制把 API Key 写进桌面程序、手机 App 或 ESP32 固件，即使代码经过混淆或“封装”，最终仍可能被设备拥有者提取。产品级密钥应保存在受控后端，设备只拿短期、受限凭证。
隐私边界本地模型可以让原始音频不离开设备；云端模型无论怎样封装，都必须把必要音频发给厂商。封装只能控制、审计和最小化外发，不能把云调用变成本地处理。
S—H

服务协议怎样选

ASR 与 TTS 的数据方向不同，通常不应机械地使用同一个接口形式。

协议优点适合
普通 HTTP简单、易调试整段音频识别、整段 TTS
HTTP chunked客户端简单，可逐块收音频流式 TTS 输出
WebSocket双向持续通信PCM 连续上传、partial/final 连续返回的 ASR
gRPC streaming强类型、双向流和取消语义清晰正式内部 ASR/TTS 服务
Queue/Pipe/UDS仅本机、开销低单机 worker MVP
S—I

Sesame Robot 的正确封装结构

业务层只依赖统一 Provider；配置决定本轮使用本地实现还是远程 API 实现。

Voice Gateway / VoiceSession ├─ AsrProvider │ ├─ LocalAsrAdapter → 本机 ASR worker/service │ └─ CloudAsrAdapter → 云 ASR WebSocket API └─ TtsProvider ├─ LocalTtsAdapter → 本机 TTS worker/service └─ CloudTtsAdapter → 云 TTS streaming API 配置： ASR_PROVIDER=local | cloud TTS_PROVIDER=local | cloud
推荐先定义统一 Provider 契约，再实现四个适配器。M1 本地实现可原生运行；远程实现只负责调用厂商 API。两种实现可以独立切换，也允许 ASR 本地、TTS 云端的混合组合。
