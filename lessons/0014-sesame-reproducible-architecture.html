14—A

先把四个前提配对

一项不一致，系统会在正确的位置拒绝你。

Gateway .env ESP32 NVS ──────────────────── ──────────────────── gateway_id ─────────────────→ gateway_id device token ←───────────────── device_token TLS cert/key ───────────────┐ mDNS hostname ───────────────┼→ root CA + hostname verification DashScope key ── Gateway only │ OpenClaw token ── Gateway only │

设备不需要 DashScope key 或 OpenClaw token。OpenClaw 也不应拿到设备 token 或 TLS 私钥。这样即使一段 Agent 配置有问题，它也不能升级成操控机器人或泄露整台电脑的权限。

从按钮到声音的实际调用链

文件路径比术语更重要，因为它让你能回到代码验证。

时刻发生什么核心文件如果失败
开机app_main() 启动网络、OLED、舵机、网页控制、AudioHal 和 VoiceController。firmware/.../main/app_main.cpp先看哪个初始化返回 ESP_ERR。

14—C

为什么不能让 ESP32 直连 OpenClaw

直连会把四个本该独立的问题绑死。

Audio

格式转换不该交给 Agent

ESP32 的 Opus 包必须被解码、限长和关联到一轮会话，ASR 才能消费；这属于 Gateway 的确定性工作。

Secrets

最小权限

设备只有自己的 token 和根证书。DashScope Key 与 OpenClaw token 留在 Mac，不会出现在固件或局域网广播中。

Control

模型输出必须二次验证

AI 回复不是硬件命令。Gateway 检查 Schema、关联 ID、声音和表情白名单；ESP32 仍检查自己的安全状态。

Recovery

断线不应等于重启

设备可以重新发现 mDNS、重建 WSS；Gateway 可以取消过期回合，避免旧 TTS 在新一轮继续播放。

14—D

复现时的工作顺序

按层做一次小验证，比一次性启动全部服务更快定位问题。

  1. 只做 build：确认 Python/uv/libopus 与 ESP-IDF 工具链，不碰密钥和硬件。
  2. 只做服务：确认 OpenClaw 是 loopback daemon，Gateway 配置完整且 healthz 可达。
  3. 只做设备连接：用安全生成的 NVS 验证 TLS/WSS 握手，不开始录音。
  4. 只做上行：按键录音后确认 Gateway 收到受限 Opus 包。
  5. 再启用 ASR、OpenClaw、TTS；每一层单独看阶段日志和错误码。
  6. 最后接功放和舵机，优先验证 stop，再做实际姿态和声音。
常见错误把 Gateway 的 .env、设备 NVS、根证书和 OpenClaw home 当作“缺失代码”从旧电脑复制。这不仅不可靠，也会把 token、Wi-Fi 密码和会话状态带入不该出现的地方。
14—E

自测：能否自己画出链路

不用背全部字段，只要能说明责任为什么放在这一层。

Gateway 为什么同时是 ESP32 的服务端、OpenClaw 的客户端？

ESP32 主动通过 WSS 连接 Gateway，所以 Gateway 监听设备路径；Gateway 又主动连接本机 OpenClaw 发起 chat.send。两条连接方向不同，Gateway 因而处在编排位置。

如果 mDNS 找到了错误 IP，应该先改模型、语音或硬件吗？

都不该。mDNS 只负责发现 LAN 地址；先检查 Gateway 广播的地址、VPN/客户端隔离和 TLS hostname。它尚未进入 ASR 或 OpenClaw。

为什么 AI 返回的字符串还不够，必须有 JSON Schema？

因为 Gateway 需要无歧义地检查它属于哪一轮、表情是否允许、速度是否在范围内，以及是否错误地请求了工具或动作。
