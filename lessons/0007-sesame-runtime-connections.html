07—A

先说当前项目的真实边界

“能力组件”“网关进程”和“监听端口”不是一回事。

组件当前形态是否监听端口
ESP32-S3WebSocket 客户端与音频设备否，由它主动连接电脑
Voice Gateway电脑上的 FastAPI 进程是，默认 0.0.0.0:8765
ASRVoice Gateway 进程内的 AsrProvider 对象否
TTSVoice Gateway 进程内的 TtsProvider 对象否

关键判断当前 ASR/TTS 只完成了“代码封装”，没有完成独立进程或独立服务封装，所以它们没有自己的 IP、端口或网关名称。
07—B

ASR/TTS 怎样封装

Pipeline 依赖稳定接口；底层模型以后可以替换，上层语音会话不用跟着改。

固定接口： AsrProvider.transcribe(PCM, AudioFormat) → AsrResult(text, confidence) TtsProvider.synthesize(text, VoiceSpec) → PCM bytes 当前实现： DemoAsrProvider → 校验 PCM，返回固定测试文字 DemoTtsProvider → 校验文本，返回静音 PCM 目标实现： LocalAsrProvider → 调用本地 ASR 模型 LocalTtsProvider → 调用本地 TTS 模型
Decode + ASR

Opus 不会直接送进 ASR

Voice Gateway 用 libopus 把每个 Opus 包解码成内存里的 16 kHz、mono、S16LE PCM，再把一段 PCM 交给 ASR Provider。

TTS + Encode

TTS 先生成 PCM

TTS Provider 返回 PCM。Gateway 每 640 bytes 切成一帧，再用 libopus 编成 Opus 包，通过原来的设备 WebSocket 返回。

当前限制libopus 编解码是真实实现；ASR 仍返回固定文字，TTS 仍生成静音，尚未接入真正的本地模型。

两条 WebSocket 连接

电脑 Voice Gateway 位于中间：对 ESP32 是服务端，对 OpenClaw 是客户端。

连接一：设备链路 ESP32 192.168.1.50:49722 ── TCP / WebSocket ──→ 电脑 192.168.1.20:8765/v1/device-stream 连接二：Agent 链路 Voice Gateway 127.0.0.1:53142 ── TCP / WebSocket ──→ OpenClaw 127.0.0.1:18789 其中 49722、53142 是操作系统临时分配的源端口； 8765、18789 是服务端稳定监听的目标端口。

07—D

监听端口与通信不是一回事

监听是等待新连接；通信发生在连接建立后产生的已连接 socket 上。

1. Voice Gateway 对 8765 执行 listen：等待设备 2. ESP32 从临时源端口 connect 到电脑 8765 3. 服务端 accept，得到一个只属于该设备的已连接 socket 4. WebSocket Upgrade 完成 5. 双方在同一个 socket 上全双工收发 6. 更多 ESP32 连接时，8765 仍继续监听，并为每台设备创建独立 socket
Listener

监听 socket

只用来接收新连接。它像前台号码，不直接代表某一次具体对话。

Connected socket

已连接 socket

由“源 IP:源端口 + 目标 IP:目标端口 + 协议”唯一标识。返回数据沿同一条连接反向发送，不需要客户端再开监听端口。

反例“两个网关都必须监听，然后相互连接”不成立。一次连接只需要一侧监听、另一侧主动连接；连接建立后天然可以双向发送。
07—E

一次完整语音回合

以下顺序对应当前软件端的执行方式。

ESP32 Voice Gateway OpenClaw │ session.hello ───────────────→│ │ │ listen.start ────────────────→│ │ │ binary(Opus × N) ────────────→│ │ │ listen.stop ─────────────────→│ │ │ │ Opus → PCM → ASR │ │ │ chat.send(text) ─────────────────→│ │ │←──────── structured answer JSON │ │ │ TTS(text) → PCM → Opus │ │←──────── asr.final / action / expression / tts.start │ │←──────── binary(Opus × N) │ │←──────── tts.stop │
协议分工WebSocket 是运输通道；JSON Schema 规定事件含义；32-byte 二进制头规定 Opus 包的方向、序号、会话和时间；Provider 接口规定本地能力怎样被调用。
07—F

从当前版走向可用版

下一步不是再增加“网关名字”，而是把真实模型、生命周期和故障隔离补齐。

建议顺序： 1. 接入真实本地 ASR/TTS Provider，先保持同进程验证纵向链路 2. 将重模型迁移为常驻 worker 进程，避免反复加载权重 3. 用 Unix domain socket 或 gRPC 定义本机 IPC 契约 4. OpenClaw 改为持久连接/连接池，并补超时、重连、取消 5. 设备链路启用 WSS、配对凭证、token 轮换和日志脱敏 6. 远程部署时再决定 VPN/Tailnet 或受控公网入口
架构立场单机阶段不需要把 ASR/TTS 都做成“网关”。它们应先是受 Voice Gateway 管理的本地能力；只有需要独立扩缩容、GPU 隔离或跨主机部署时，再升级为独立服务。
