Wi-Fi 掉线，
先别急着怪路由器

你的机器人当前有一个更直接的软件问题：它第一次连上 Wi-Fi 后，把“断线提醒器”拆掉了。以后真掉线，机器人就不知道自己该重连。

约 10 分钟面向初学者基于当前 ESP32-S3 固件
12—A

先看整条通信链路

一次“能和机器人说话”的过程，其实有三段连接。

机器人 ESP32-S3 │ Wi-Fi（连接家里的路由器） ▼ 路由器 / 局域网 │ Internet / 局域网 TCP ▼ 电脑上的 Voice Gateway │ WebSocket（WSS，长连接） ▼ 语音服务、Agent、TTS

所以“机器人没反应”不一定等于 Wi-Fi 掉了。可能是第一段 Wi-Fi 断了，也可能是 Wi-Fi 还在、但第三段 WebSocket（网页/程序的长连接）断了。

看到的现象可能含义先看什么
机器人重启、串口从开机日志重新开始供电掉压或 brownout（欠压复位）3.3 V、电源线、LDO、舵机/功放动作
机器人没重启，但显示 Wi-Fi disconnectedESP32 与路由器的 Wi-Fi 断开断开原因码、RSSI、路由器
Wi-Fi 仍有 IP，语音却不工作WebSocket / Gateway 连接断开Gateway 与 WSS 日志
12—B

当前代码到底哪里有问题

把它理解成“保安下班了”。

开机 → 注册 Wi-Fi 事件处理器（安排一个保安守着） → 连上 Wi-Fi，拿到 IP → 注销事件处理器（保安下班） ← 当前代码的问题 → 后来 Wi-Fi 断开 → 没人收到消息，也就没人执行重连

“事件处理器”不是一个神秘硬件。它只是程序里的一段回调函数：系统发生某件事时，自动叫它来处理。这里的事包括“Wi-Fi 断开”和“重新拿到 IP”。

当前代码确实写了：断线后调用 esp_wifi_connect()。但它只在第一次连网之前有效，因为第一次获得 IP 后就被注销了。因此不是“完全没有重连代码”，而是“重连代码活得太短”。

第二个问题当前代码没有打印断开的真正原因。例如密码不对、信号差、路由器踢人、路由器重启，日志看起来都可能只是“掉了”。不先记录原因，后面就只能猜。
12—C

正确的重连过程是什么

不是“疯狂点连接”，而是有节奏地重新排队。

Wi-Fi 断开 │ ├─ 记下原因、信号强度、失败次数 ├─ 告诉 WebSocket：旧连接已失效 └─ 等待 1 秒后重连 失败 → 等 2 秒 → 4 秒 → 8 秒……（设上限） │ ▼ 再次拿到 IP │ ▼ 重新连接 Voice Gateway（WSS）

为什么要等一会儿？如果是路由器刚重启，它需要时间恢复。如果程序每一毫秒就重连一次，只会制造更多失败日志，还会让扫描 Wi-Fi 的功能无法工作。官方也建议应用自己设计有上限的重连策略。

为什么要“重新建立 WSS”？因为 Wi-Fi 断开时，ESP-IDF 会清理原有 TCP 连接。即使稍后又连回了同一个路由器，旧的 WebSocket 也不能当作还活着。

12—D

拿到断开原因后，怎么理解

原因码像医院的化验单：它不能包治百病，但能告诉你该查哪一科。

日志中的原因日常说法先做什么
BEACON_TIMEOUT很久没有听到路由器的“我还在”广播看 RSSI、距离、天线、2.4 GHz 干扰、AP 是否重启
NO_AP_FOUND没找到要连的 Wi-Fi确认独立 2.4 GHz、SSID 没隐藏、信道和信号
AUTH_FAIL / HANDSHAKE_TIMEOUT密码或加密握手没有谈成查密码、WPA2/WPA3、PMF 和路由器设置
ASSOC_TOOMANY路由器说“接入设备太多”查客户端上限、访客网络、接入控制
reset / brownout不是 Wi-Fi 先坏，是芯片因为电压不稳重启先测 3.3 V，不要先改 Wi-Fi 代码
12—E

“关闭 Wi-Fi 省电”是什么意思

它是排查开关，不是万能药。

ESP32 默认会让 Wi-Fi 芯片周期性休息，省电但会带来接收延迟。对电池设备这是好事；对你的语音机器人，实时响应更重要，所以可以试验：

ESP_ERROR_CHECK(esp_wifi_set_ps(WIFI_PS_NONE));

这句话的意思是：Wi-Fi 不要为了省电而睡觉。它会更耗电，所以要做对比试验：默认模式跑一天，再关闭省电跑一天，记录掉线次数、掉线原因和耗电。如果两者没有差别，就不要因为“网上说有用”而永久关闭。

你现在只要记住

先修“保安下班”的代码错误；再测试省电；最后才把重点放到路由器、天线和供电。顺序不能反。

12—F

硬件为什么也会让 Wi-Fi 看起来掉线

Wi-Fi 发射瞬间需要的电流会变大，机器人又有音频、舵机和功放。

ESP32-S3 使用 3.3 V。官方建议供电能力不少于 500 mA，并在电源入口和芯片附近加入去耦电容。若舵机或功放一动作，电压下陷，ESP32 可能直接重启；用户看起来就像“Wi-Fi 忽然断了”。

  1. 先看串口：掉线前后是否重新出现启动日志或 brownout。
  2. 把机器人去壳、放到路由器旁边测试；不要一开始在复杂环境里猜。
  3. 临时停用电机/舵机和蓝牙，观察断线是否消失。
  4. 用独立的 2.4 GHz、WPA2/AES、非隐藏 SSID 做一次对照。
  5. 还不稳定，再用示波器测 ESP32 芯片附近 3.3 V，而不是只在电源插头处测。
12—G

这段代码具体怎么改

核心不是多写一行 esp_wifi_connect()，而是让值班员一直在岗。

当前 connect_wifi() 在第一次连接后注销事件处理器并释放 event group。正确改法是把“事件处理器、event group、重连次数、重连定时器”放进 GatewayClient 成员中，让它们和整个 Voice Gateway 会话同寿命。

// 断线事件：只负责记录和安排下一次重连
on_wifi_disconnected(event_data) {
  reason = event_data.reason;
  log(reason, rssi, bssid, attempts);
  mark_wss_offline();
  schedule_after(reconnect_delay_ms(attempts++)); // 0.5/1/2/4/.../30 秒
}

// 定时器到点：真正调用连接 API
on_reconnect_timer() {
  esp_wifi_connect();
}

// 拿到 IP：说明网络层恢复，业务层可以继续连 WSS
on_got_ip() {
  attempts = 0;
  mark_wifi_online();
  // 已有 WSS 自动重连配置时，让它自行完成重连；
  // 否则在这里启动或重建 WSS。
}
不要这样改不要在断线回调内无限、立刻重复 esp_wifi_connect()；也不要继续把 context 指向函数内的局部 event group。函数返回后它已经不存在，后续回调会变成悬空引用。

在当前项目里，还要移除首次连上后 esp_event_handler_instance_unregister(...) 和 vEventGroupDelete(group) 的那段清理；清理应移动到 GatewayClient::stop()，即真正关闭整个连接会话时才执行。

12—H

Wi-Fi 休眠后，谁来唤醒它

先区分“无线电小睡”和“整颗芯片睡死”。

模式CPU / Wi-Fi 状态如何醒来适不适合语音机器人
WIFI_PS_MIN_MODEM（默认）Wi-Fi 无线电定期休息；不是深度关机自动按路由器 DTIM/beacon 节奏醒来接收数据可用，但要实测延迟与兼容性
WIFI_PS_NONEWi-Fi 不进入 modem-sleep不需要唤醒实时语音排查/常态的优先候选，代价是耗电
系统 Light-sleepCPU 暂停，配置决定哪些外设继续运行定时器、GPIO、部分 Wi-Fi MAC 事件等当前项目未启用；不作为本次修复手段
Deep-sleepWi-Fi 与主 CPU 都关闭，醒后相当于重新启动RTC 定时器、外部 GPIO 等硬件唤醒源不适合等待语音/WSS 长连接

所以，若你调用 esp_wifi_set_ps(WIFI_PS_NONE)，根本不会进入 Wi-Fi modem-sleep，也就没有“怎么唤醒”的问题。若保持默认 WIFI_PS_MIN_MODEM，ESP32 会自己在每个 DTIM（路由器周期性广播的接收时刻）醒来；程序不需要写一个“唤醒 Wi-Fi”的函数。

当前工程的 CONFIG_PM_ENABLE 没有启用，表示没有在使用系统级的自动 Light-sleep。此处讨论的只是 Wi-Fi 自己的省电，不会让机器人程序、舵机控制或 Voice Gateway 逻辑全部停止。
