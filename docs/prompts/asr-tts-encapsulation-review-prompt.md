# ASR / TTS 封装架构评审任务说明

请把下面内容视为一份架构分析任务，而不是直接写代码的要求。

## 你的角色

你是一名熟悉端侧语音系统、流式音频、云端 AI API 和安全隐私的系统架构师。请直接指出设计中的问题和权衡，不要为了迎合我而默认所有设想都正确。

## 项目背景

我正在设计一个语音机器人系统：

- ESP32 负责采集和播放音频；
- 音频通过 Opus 和 WSS 在 ESP32 与电脑或服务器之间传输；
- Voice Gateway 负责语音会话、音频格式转换、ASR、Agent、TTS、打断、队列和错误处理；
- ASR 将语音转换为文本；
- Agent（例如 OpenClaw）只处理文本和工具调用，不直接处理 PCM 或 Opus；
- TTS 将 Agent 的回复文本转换为语音，再发送给 ESP32 播放。

## 我的真实意图

我不是只想知道“有哪些 ASR/TTS 模型”，也不是只想把某个云 API 包一层 HTTP 接口。

我想把 **ASR 和 TTS 分别设计成独立、可替换的能力模块**。每个模块都要同时支持两类实现：

1. **本地实现**：模型在端侧电脑运行，使用本地 CPU、GPU、NPU 或统一内存完成推理；
2. **云端实现**：本地程序通过网络调用第三方 ASR/TTS API，模型推理由云厂商完成。

Voice Gateway 不应直接依赖某个模型、SDK 或云厂商，而只依赖统一的内部接口，例如：

```text
AsrProvider
├── LocalAsrProvider
└── CloudAsrProvider
    ├── VendorAAsrAdapter
    └── VendorBAsrAdapter

TtsProvider
├── LocalTtsProvider
└── CloudTtsProvider
    ├── VendorATtsAdapter
    └── VendorBTtsAdapter
```

系统应允许 ASR 和 TTS 独立选择来源，例如：

```text
ASR_PROVIDER=local|cloud
TTS_PROVIDER=local|cloud
```

因此可以出现“本地 ASR + 云端 TTS”或“云端 ASR + 本地 TTS”，而不是把二者绑定为同一种部署方式。

## 我所说的“封装”

请严格区分以下概念：

1. **代码和接口封装**：用稳定的 Provider 接口隔离模型、SDK、厂商协议和业务代码。这是本任务的核心。
2. **进程或服务封装**：把能力做成独立进程，通过 localhost HTTP、WebSocket、gRPC 或 IPC 调用。这是可选的部署边界。
3. **容器封装**：使用 Docker 固定运行环境和依赖。这是部署手段，不等于完成了接口封装。
4. **安全封装**：集中处理凭证、鉴权、授权、限流、日志脱敏和数据策略。它依赖清晰边界，但不能仅靠“多包一层代码”自动实现。

这里的 API 也可能指三种不同东西：

- Python/C#/Go 进程内函数或类接口；
- 本机 localhost 服务 API；
- 第三方云厂商的远程 API。

请不要把它们混为一谈。

## 为什么必须封装

我希望你验证并完善以下判断：

- 隔离模型和厂商差异，避免 VoiceSession 到处出现厂商 SDK、请求参数和响应 JSON；
- 统一音频输入输出契约，例如 PCM、采样率、位深、声道、chunk 时长和时间戳；
- 统一流式事件，例如 ASR partial/final、TTS audio chunk、完成、取消和错误；
- 本地实现集中管理模型加载、预热、设备选择、显存或内存、并发和卸载；
- 云端实现集中管理认证、连接、重试、超时、限流、配额和厂商错误映射；
- 支持依赖替换、Fake Provider、契约测试、性能指标和故障注入；
- 把隐私和安全策略放在唯一受控的出口，而不是散落在业务代码中；
- 本地模型或云服务以后发生变化时，尽量不修改上层会话流程。

如果不封装，预期风险包括：

- Voice Gateway 与特定模型或云厂商紧耦合；
- PCM、WAV、MP3、Opus 和不同采样率被混用；
- 厂商 JSON 或本地 tensor（张量）泄漏到业务层；
- 每次请求重复加载本地模型，造成延迟、内存浪费或 OOM；
- 同步推理阻塞事件循环，并发状态互相污染；
- TTS 被打断后仍继续生成和播放旧音频；
- 云端超时、限流和断线直接击穿整个语音会话；
- API Key 出现在客户端、代码仓库或日志中；
- 系统未经用户同意自动从本地切到云端，导致原始音频或文本外发；
- 无法使用统一测试验证不同 Provider 的行为。

请判断这些风险是否准确，有遗漏就补充。

## 本地实现与云端实现的关键区别

### 本地实现

- 模型权重和推理运行时部署在端侧电脑；
- 会使用本地 CPU、GPU、NPU、内存和磁盘；
- 原始语音可以不离开本地，隐私控制更强；
- 需要自己处理模型生命周期、资源竞争、量化、并发、崩溃恢复和性能优化；
- 可以先采用进程内适配器；依赖冲突、崩溃隔离或多语言调用明显时，再拆成本机服务。

### 云端实现

- 模型权重和主要推理算力在云厂商侧；
- 本地通常不需要承担模型推理，但仍要完成录音、Opus/PCM 编解码、重采样、VAD/AEC、网络传输、缓冲、取消和播放；
- 音频或文本必须发送给云厂商，因此要明确用户同意、数据用途、保存周期、删除机制和供应商策略；
- 永久的云厂商 API Key 不应放入 ESP32、前端、手机 App 或交付给用户控制的桌面客户端；
- 产品化时优先由自己的后端代理调用厂商 API，或由后端签发短期、受限凭证；个人原型至少使用环境变量或系统 Keychain，不写入源码和日志。

## 安全与用户数据保护的边界

我需要你明确解释：

**接口封装能建立统一的安全控制点，但它本身不等于完成了安全和隐私保护。**

至少要分别分析：

### 保护自己的 API 和云厂商凭证

- TLS/WSS；
- 设备和用户身份认证；
- 授权与租户隔离；
- 短期 token 或请求签名；
- 限流、配额和费用控制；
- 参数、音频大小和格式校验；
- 防重放和异常调用检测；
- Secret Manager、环境变量或系统 Keychain；
- 日志中不记录 Key、token 和敏感请求头。

### 保护用户数据

- 明确哪些数据会离开设备：原始音频、转写文本、合成文本、TTS 音频和元数据；
- 默认数据最小化，只发送完成任务所必需的数据；
- 本地与云端切换必须受显式策略控制，不得静默上传；
- 传输加密、必要时静态加密；
- 数据保存周期、缓存 TTL、删除和导出机制；
- 日志和监控脱敏；
- 用户、设备和租户之间的数据隔离；
- 对第三方云厂商的数据处理条款和保留策略进行核查。

请区分“保护 API 入口”和“保护用户数据整个生命周期”，不要将二者视为同一件事。
